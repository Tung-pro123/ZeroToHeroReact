## 🌟 TỔNG QUAN BÀI HỌC

Tổ chức State tốt là ranh giới phân định rõ ràng giữa một Component thanh lịch, dễ bảo trì và một Component chắp vá, liên tục phát sinh bug ngầm.

Khi bạn thiết kế cấu trúc State bừa bãi:
1. Bạn phải viết hàng tá hàm `useEffect` hoặc logic lằng nhằng để cố gắng giữ 2-3 biến State đồng bộ với nhau.
2. Dữ liệu một nơi cập nhật nhưng nơi khác vẫn giữ giá trị cũ (Lỗi lệch pha / Desynchronization).
3. Code cập nhật mảng hoặc object lồng sâu trở thành "cơn ác mộng" đệ quy.

> [!TIP]
> **Triết lý cốt lõi:**  
> Thiết kế State trong React giống hệt như **Chuẩn hóa Cơ sở Dữ liệu (Database Normalization)**:  
> *"Hãy làm cho State đơn giản nhất có thể, nhưng không được phép đơn giản hơn."*

## 1. 5 NGUYÊN TẮC VÀNG KHI THIẾT KẾ STATE

```mermaid
mindmap
  root((5 Nguyên Tắc Thiết Kế State))
    1. Gộp State Liên Quan
      position: {x, y}
      Luôn thay đổi cùng nhau
    2. Tránh Nghịch Lý
      Finite State Machine
      status: typing | sending | sent
    3. Xóa Bỏ State Thừa
      Derived State
      fullName = first + last
    4. Tránh Trùng Lặp
      Lưu selectedId
      Không lưu cả Object clone
    5. Làm Phẳng Dữ Liệu
      Flatten / Normalize
      Thay Tree bằng Hash Map
```

### Nguyên tắc 1: Gộp các State liên quan mật thiết (Group related state)
* Nếu 2 hoặc nhiều biến State **luôn luôn thay đổi cùng một thời điểm**, hãy gộp chúng vào một Object:
  ```javascript
  // ❌ RỜI RẠC:
  const [x, setX] = useState(0);
  const [y, setY] = useState(0);

  // ✅ GỘP GỌN:
  const [position, setPosition] = useState({ x: 0, y: 0 });
  ```

### Nguyên tắc 2: Tránh các State gây ra nghịch lý (Avoid contradictions in state)
* Nếu cấu trúc State cho phép tồn tại một **"Trạng thái không tưởng" (Impossible State)**, đó là một thiết kế tồi:
  ```javascript
  // ❌ NGHỊCH LÝ: isSending = true và isSent = true cùng lúc được không?
  const [isSending, setIsSending] = useState(false);
  const [isSent, setIsSent] = useState(false);

  // ✅ CHUẨN: Dùng 1 biến trạng thái hữu hạn duy nhất
  const [status, setStatus] = useState('typing'); // 'typing' | 'sending' | 'sent'
  ```

### Nguyên tắc 3: Xóa bỏ State thừa - Tận dụng Derived State (Avoid redundant state)
> [!CRITICAL]
> **Định luật tối thượng:** Nếu một giá trị có thể tính toán được từ Props hoặc các State khác trong quá trình Render, **TUYỆT ĐỐI KHÔNG ĐƯỢC BIẾN NÓ THÀNH STATE**.

* **Ví dụ Họ và Tên:**
  ```javascript
  // ❌ THỪA THÃI VÀ DỄ LỆCH PHA:
  const [firstName, setFirstName] = useState('');
  const [lastName, setLastName] = useState('');
  const [fullName, setFullName] = useState(''); // Thừa! Phải cập nhật ở 2 nơi!

  // ✅ TỐI ƯU: Tính toán trực tiếp lúc render
  const [firstName, setFirstName] = useState('');
  const [lastName, setLastName] = useState('');
  const fullName = `${firstName} ${lastName}`.trim();
  ```

### Nguyên tắc 4: Tránh trùng lặp dữ liệu - Lưu ID thay vì Object (Avoid duplication in state)
* Khi bạn có một danh sách các món đồ và một mục đang được chọn, **chỉ lưu ID (Khóa chính) của mục đó**:
  ```javascript
  // ❌ TRÙNG LẶP NGUY HIỂM:
  const [items, setItems] = useState([{ id: 1, name: 'Snack' }]);
  const [selectedItem, setSelectedItem] = useState(items[0]); 
  // BUG: Nếu người dùng sửa tên Snack thành Bánh mì trong mảng items,
  // selectedItem vẫn giữ chữ 'Snack' cũ -> Mất đồng bộ!

  // ✅ CHUẨN MỰC: Chỉ lưu selectedId
  const [items, setItems] = useState([{ id: 1, name: 'Snack' }]);
  const [selectedId, setSelectedId] = useState(1);

  // Tính toán trực tiếp object đang chọn lúc render:
  const selectedItem = items.find(item => item.id === selectedId);
  ```

### Nguyên tắc 5: Tránh State lồng nhau quá sâu - "Làm phẳng" dữ liệu (Avoid deeply nested state)
* Cấu trúc lồng sâu (Nested Tree) biến thao tác cập nhật bất biến thành ác mộng.
* Hãy **làm phẳng (Flatten / Normalize)** cấu trúc thành dạng Bảng (Table / Hash Map) giống như CSDL quan hệ SQL:

```javascript
// ❌ CẤU TRÚC CÂY LỒNG NHAU (Rất khó cập nhật):
const places = {
  id: 0,
  title: 'Trái Đất',
  childPlaces: [
    { id: 1, title: 'Châu Á', childPlaces: [{ id: 2, title: 'Việt Nam' }] }
  ]
};

// ✅ CẤU TRÚC LÀM PHẲNG (NORMALIZED STATE):
const placesById = {
  0: { id: 0, title: 'Trái Đất', childIds: [1] },
  1: { id: 1, title: 'Châu Á', childIds: [2] },
  2: { id: 2, title: 'Việt Nam', childIds: [] }
};

// Cập nhật tên 'Việt Nam' siêu tốc O(1):
setPlacesById({
  ...placesById,
  2: { ...placesById[2], title: 'Việt Nam (VN)' }
});
```

## 2. CẠM BẪY PHỔ BIẾN: ĐƯA PROP VÀO STATE BAN ĐẦU

Xét đoạn mã nguồn cực kỳ phổ biến ở người mới:
```javascript
function Message({ messageColor }) {
  // ❌ CẠM BẪY NGẦM:
  const [color, setColor] = useState(messageColor);
}
```

### 2.1 Tại sao đây là lỗi?
`useState(messageColor)` chỉ đọc giá trị của `messageColor` ở **lần render ĐẦU TIÊN DUY NHẤT** khi component được gắn (Mount) vào DOM.  
Nếu sau đó component Cha truyền xuống một màu mới (ví dụ đổi từ `'blue'` sang `'red'`), biến `color` bên trong con **vẫn giữ nguyên là `'blue'` cũ** và không bao giờ tự cập nhật theo!

### 2.2 Cách giải quyết chuẩn:
1. **Nếu muốn luôn đồng bộ với Cha:** Dùng trực tiếp Prop, không tạo State!
   ```javascript
   function Message({ messageColor }) {
     const color = messageColor; // Luôn luôn đồng bộ theo Cha!
   }
   ```
2. **Nếu cố tình chỉ muốn lấy làm giá trị khởi tạo ban đầu:** Đổi tên prop thành `initialColor` hoặc `defaultColor` để báo hiệu rõ ràng cho các lập trình viên khác:
   ```javascript
   function Message({ initialColor }) {
     const [color, setColor] = useState(initialColor);
   }
   ```

## 3. TỐI ƯU HÓA: MULTIPLE SELECTION VỚI JAVASCRIPT `SET`

Khi xây dựng tính năng chọn nhiều phần tử (như chọn nhiều email trong hộp thư để xóa hàng loạt):
* Nếu dùng mảng `[1, 5, 8]`: Muốn kiểm tra item có đang được chọn hay không (`arr.includes(id)`) phải mất độ phức tạp thời gian $O(N)$.
* **Dùng cấu trúc dữ liệu `Set`:** Độ phức tạp tìm kiếm `set.has(id)` chỉ là **$O(1)$ siêu tốc**!

```javascript
const [selectedIds, setSelectedIds] = useState(new Set());

function handleToggle(id) {
  const next = new Set(selectedIds); // Copy Set
  if (next.has(id)) {
    next.delete(id); // Bỏ chọn
  } else {
    next.add(id); // Chọn
  }
  setSelectedIds(next);
}
```

## 4. GÓC NHÌN SENIOR: ĐỐI CHIẾU VỚI DATABASE NORMALIZATION (3NF)

Sự tương đồng giữa React State Structure và Thiết kế Cơ sở Dữ liệu quan hệ (RDBMS):

| Nguyên lý React State | Chuẩn hóa CSDL (Database 3NF) |
| :--- | :--- |
| **Xóa bỏ Derived State** (`fullName`) | Không lưu cột có thể tính toán (`total_amount = qty * price`) |
| **Lưu `selectedId` thay vì Object** | Dùng Khóa ngoại (Foreign Key: `user_id`) thay vì nhúng toàn bộ thông tin User vào bảng Order |
| **Làm phẳng Normalized State** | Tách các bảng quan hệ 1-N (Bảng `Places` và danh sách `child_ids`) để tránh lặp dữ liệu |

## 5. BỘ CÂU HỎI PHỎNG VẤN SENIOR REACT DEVELOPER

### Q1: Tại sao lưu `selectedId` trong State lại vượt trội hơn lưu cả object `selectedItem`?
* **Đáp án:**
  1. **Tránh lỗi Desynchronization:** Nếu thuộc tính của item bị sửa trong danh sách gốc, biến `selectedItem` cũ sẽ bị lỗi thời vì là 2 object khác nhau. Lưu `selectedId` đảm bảo luôn lấy được dữ liệu mới nhất thông qua phép `find()`.
  2. **Tiết kiệm bộ nhớ:** Chỉ lưu 1 số nguyên/chuỗi ID thay vì nhân bản cả một object to lớn.

### Q2: Khi nào thì nên dùng cấu trúc Normalized State thay vì Nested State?
* **Đáp án:** Khi dữ liệu có quan hệ cha-con lồng nhau sâu (như cây thư mục, bình luận lồng nhau Reddit, cấu trúc địa lý) hoặc cùng một đối tượng xuất hiện ở nhiều nơi trên màn hình. Normalized State giúp việc thêm, sửa, xóa bất kỳ node nào đều đạt độ phức tạp $O(1)$ mà không cần duyệt cây đệ quy.
